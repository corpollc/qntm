# Signing-key and signature validation

The maintained TypeScript and Python clients use the same Ed25519 acceptance
rules as the Go charter registry. This is an unreleased hardening change for
messaging and relay authentication; the charter already used these rules.

Public keys must be 32-byte canonical encodings of nonidentity points in the
prime-order subgroup. Signatures must be 64 bytes, with canonical `R` and
`0 <= S < L`. `R` must also be in the prime subgroup, where the identity is
allowed. Verification uses the uncofactored Ed25519 equation. This deliberately
excludes permissive ZIP-215 acceptance. RFC 8032 permits the uncofactored check;
the additional public-key restriction defines qntm's identity profile.
[RFC 8032, section 5.1.7](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7).

In TypeScript, `isValidEd25519PublicKey` and `verifyEd25519Signature` are exported
from both `@corpollc/qntm` and `@corpollc/qntm/crypto`. Python exports
`is_valid_ed25519_public_key` and `verify_ed25519_signature` from `qntm`.
These functions return booleans. Charter validation retains its exception
contract for invalid authority keys.

QSP message verification, gateway request and governance signatures, and
announcement verification use this shared profile. The relay uses the same
TypeScript verifier for optional subscription challenges, read receipts and
announcement management. Invite import, gateway identity/context checks and
group member admission reject invalid signing keys before granting authority.
Group roster parsing also checks that each member ID matches its public key;
an invalid later entry cannot cause a partial roster update.

TypeScript checks both public-key and `R` subgroups before using Noble's strict
verification mode. With both points in the prime subgroup, Noble's cofactored
check is equivalent to the uncofactored equation. Python uses library point
operations before OpenSSL verification, including libsodium's documented
workaround for older versions with permissive mixed-order point validation.
[Noble documentation](https://github.com/paulmillr/noble-curves#ed25519-x25519--ristretto255),
[libsodium point validation](https://doc.libsodium.org/advanced/point-arithmetic#point-validation).

TypeScript remembers at most 256 valid public-key encodings in process memory
to avoid repeating expensive subgroup checks during checkpoint and roster
validation. Entries contain public bytes only and are not persisted or logged.
Changing a caller's key buffer causes a new lookup. Every signature is still
verified against its message, and membership, policy and freshness checks are
unchanged; this cache cannot grant or preserve authority.

## Compatibility and limits

Keys and signatures generated by the maintained clients keep the same bytes
and remain valid. No message field, key derivation or cipher changes. Imported
malformed keys and signatures that depended on permissive verification are
now rejected, including in saved-history verification. This does not rotate
existing keys, delete history, or establish group membership merely from a
valid signature. The archived Go messaging client is not maintained; the Go
implementation covered here is the charter registry.

The regression cases demonstrate acceptance differences for deliberately
constructed weak keys and malformed signatures. They do not demonstrate
forgery of a properly generated, pinned participant key. Possession of group
encryption keys still allows an insider to construct ciphertext, so recipients
must verify the inner signature and the applicable membership policy.

## Evidence and deployment

The [shared vectors](../specs/test-vectors/ed25519-verification.json) include
an RFC 8032 known-answer signature, canonical identity `R`, weak/noncanonical
public keys, torsion `R`, noncanonical scalars and length errors. TypeScript,
Python and Go execute the same vectors. Additional tests put a synthetic
identity-key forgery inside valid authenticated ciphertext and submit forged
receipts, announcement registrations and subscription responses to a real
local Worker. All fixture keys are public synthetic test material.

Build `client` before starting or deploying `worker`; the relay imports the
packaged verifier rather than maintaining a separate copy. The relay deployment
workflow installs and builds the client before its dry run and deployment.
Package publication, browser/gateway deployments and relay deployment are
separate operations: changing source alone does not update installed clients
or running services.
