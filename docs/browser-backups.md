# Browser backups

In **Settings → Backup & Restore**, enter and confirm a unique password of at least 12 characters, then choose **Export encrypted backup**. Keep the password separately. qntm cannot recover a forgotten password. Export and import run locally; no backup or password is uploaded.

To restore, select the JSON file and enter its password. Older unencrypted JSON backups are supported with an empty password. Choose **Review backup** to validate it and see current versus replacement profile, conversation, message and guidance-contact counts. The review lists restored identity key IDs, relay URL, gateway identities and any pending gateway endpoint, plus every guidance recipient key ID, conversation and relay. It never displays private keys or message contents. A pin whose conversation is unavailable remains unusable until its destination is verified through the normal guidance flow.

Restoring replaces messaging state; it does not merge histories. Cancel leaves existing data intact. Replacement requires an explicit trust acknowledgement and **Replace browser data**. If another tab or an incoming message changes the stored state after review, restore stops and requires a new review. A storage-quota failure leaves the previous value intact. Display preferences stored outside `aim-store` are not part of this format.

Files are limited to 10 MiB, including encryption overhead. Validation checks field types and bounds, identity key-pair consistency, conversation key lengths, timestamp/epoch/cursor shapes, gateway identity/context, guidance destinations, and profile references. Unknown fields and versions are rejected rather than silently discarded. The older format without `guidanceContacts` is accepted. Validation does **not** prove that a backup's plaintext history, local names or claimed gateway state is trustworthy: restore only files you trust. An attacker who can construct or alter local state can invent that history.

## Encryption and remaining exposure

New browser downloads use the Web Crypto API: AES-256-GCM with a fresh random 12-byte nonce, a 128-bit authentication tag, and a password-derived key from PBKDF2-HMAC-SHA-256 with 600,000 iterations and a fresh 16-byte salt. The version and algorithm parameters are authenticated as associated data and the importer accepts only the fixed supported parameters, preventing a file from choosing an unbounded derivation cost. [Web Crypto derivation](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/deriveKey), [OWASP PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2).

The JSON wrapper has `format: "qntm-aim-backup"`, `version: 1`, `kdf: "PBKDF2-SHA256"`, `iterations: 600000`, `cipher: "AES-256-GCM"`, and unpadded base64url `salt`, `iv` and `ciphertext` (including the tag). Associated data is the UTF-8 string `qntm-aim-backup:1:PBKDF2-SHA256:600000:AES-256-GCM`. The wrapper reveals its format, parameters and ciphertext size; the download filename includes its export date. Password text is encoded as UTF-8 without normalization.

This protects downloaded files, not an unlocked browser. Browser `localStorage` and in-memory state still contain private keys and plaintext history. A compromised browser, extension or device can access them. Legacy backups and the low-level programmatic `api.exportBackup()` remain plaintext; that raw API is intended for local tooling, while the Settings download always uses encryption. Keep existing plaintext copies private or replace them with encrypted backups. See the [metadata inventory](metadata-privacy.md) for the different relay and provider boundaries.
