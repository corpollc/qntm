# qntm v0.9.0-beta.1

This beta adds optional charter discovery and
hardens the messaging clients, gateway and relay following independent Claude
and Grok source audits. Python uses the equivalent version `0.9.0b1`.

## Optional charter discovery

Receivers generate `charter_info` from the authenticated sender key ID and the
fixed registry origin. Reserved fields supplied by a sender cannot override it;
attempted overrides are flagged. Chartering is optional. Sending messages adds
no HTTP round trip or model assessment. The reminder does not assert charter
availability or compliance.

Charter JSON remains policy data for applications that choose to assess it.
The libraries do not run an agent or model assessment. The registry remains
experimental and unwitnessed.

## Security and recovery

Gateway thresholds require positive safe integers. Durable replay checks prevent
old messages from restoring votes or resetting credential lifetimes. Membership
state, rekeys and ordered publication records commit together. Completed API
results are retried for delivery without repeating the API call; unknown external
outcomes stay blocked for operator review. Responses are bounded and redirects
cannot forward vault credentials.

Python, browser, terminal and OpenClaw clients enforce authenticated group
authority and exact rekey membership. Stale gateway acceptances cannot replace a
newer roster. Cached channel notifications remain bound to their authenticated
ciphertext. Entity-to-sender verification requires an explicit trusted binding
verifier, independently of an entity's active registry status.

## Upgrade considerations

- New announcement IDs are the first 16 bytes of
  `SHA-256("qntm-announce-v1|id|" + base64url(master_public_key))`. A master key
  cannot claim an arbitrary direct/group conversation ID. Legacy unbound
  announcement claims are quarantined; recreate those channels and distribute
  new invitations. Quarantine does not delete retained conversation data.
- Active gateways own the membership transition path. Group membership
  delegation requires the creator's signed invitation; participant-only or
  legacy invitations permit API use but do not enable gateway membership
  changes. Standalone administrator/member controls are rejected while a
  gateway is active. Use a fresh, creator-invited gateway conversation when
  upgrading an older deployment that needs membership governance.
- Stored pre-upgrade gateway actions seed replay protection. Reissuing an old
  signed action is not a fresh vote; create a new request/proposal when needed.
  Credentials created before replay protection was installed may need fresh
  provisioning.
- Any current participant can still replace a service credential. Credential
  replacement/revocation is not yet quorum-governed. Untrusted `did:web`
  resolution still requires an appropriate caller-controlled egress policy.

## Compatibility with 0.6.x

Ordinary encrypted message framing remains protocol version 1 / `QSP-1`.
Sixteen bidirectional Python exchanges passed between this beta and each of
`v0.6.0`, `v0.6.1`, `v0.6.2` and `v0.6.3`: direct and group text, with invitations
created by either version. These checks used archived release sources in the
current test environment. They do not establish compatibility for every adapter,
old dependency environment, mixed-version governance or deployed service.

Some integrations require changes:

| Integration | Upgrade effect |
| --- | --- |
| Receive JSON / SDK results | Locally generated `charter_info` adds a field. Strict consumers that reject unknown fields need a schema update. It is not an extra wire-protocol field and does not require a charter lookup. |
| Announcement channels | The upgraded relay rejects arbitrary new IDs and quarantines legacy unbound channels. Existing 0.6.x clients can be affected by a shared relay upgrade without changing their installed package. Migrate channels as described above. |
| Gateway/group membership | Legacy or non-creator invitations no longer establish gateway membership authority; parallel standalone controls are rejected once a gateway is active. Existing groups may require a fresh creator-invited gateway conversation. |
| Gateway execution | Invalid thresholds, replayed actions, redirecting targets and expired credentials no longer retain their earlier behavior. Response bodies are capped at 8 KiB. Review affected recipes and reprovision old credentials as needed. |
| Python entity verification | `verify_sender_entity` requires both DID resolution and an explicit trusted `verify_binding_fn`; missing verification returns false. Use `verify_entity` for a status-only lookup. |
| CLI identity automation | Generating an identity over an existing identity now fails instead of overwriting it. |

Keep the beta opt-in. A package version pin protects against a client upgrade,
but not against changes to a shared relay or gateway. Shared-service rollout
needs migration and mixed-version governance checks before it can be described
as compatible with existing 0.6.x deployments. No shared service was deployed
as part of this release preparation.

See the [audit report](../audits/2026-10-30-charter-release-audit.md) for verification
and remaining boundaries. This beta is not a production deployment announcement.

```sh
pip install --upgrade qntm==0.9.0b1
npm install @corpollc/qntm@0.9.0-beta.1
```
