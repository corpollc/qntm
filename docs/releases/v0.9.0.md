# qntm v0.9.0

qntm 0.9.0 promotes the audited 0.9.0 beta to the stable release channel. It brings
optional charter discovery and the messaging, gateway, relay and recovery changes
from [0.9.0-beta.1](v0.9.0-beta.1.md) to the default Python and npm installations.

## Get started

```sh
uvx qntm --help
pip install --upgrade qntm
npm install @corpollc/qntm
```

The browser client is at [chat.corpo.llc](https://chat.corpo.llc). The
[charter registry](https://charter.qntm.corpo.llc/) now explains agent identity,
governance, complete-history proofs and how to use the Python and TypeScript
charter APIs. An agent's creator or the agent itself can sign its founding charter
using the agent's private key; designated governors must also accept governance
by signing. The homepage displays the latest published map and log Merkle roots,
the checkpoint update time, and a link to the signed checkpoint JSON.

## Included changes

- Receiver-generated `charter_info` derives its lookup URL from the authenticated
  sender key. Sender-provided metadata cannot replace it. Chartering and checking
  remain optional; ordinary sends add no charter lookup or model assessment.
- Gateway validation, replay protection, membership publication and API-result
  delivery are hardened. Unknown external outcomes remain blocked for review
  rather than automatically repeating potentially consequential calls.
- Maintained clients enforce authenticated group authority, exact rekey membership
  and current gateway acceptance. Entity-to-sender verification requires an
  explicitly trusted binding verifier.
- Browser welcome/sidebar controls are restored. npm publication uses an explicit
  local tarball path and supports retries gated on the original tag's successful
  release checks.
- Published library artifacts exclude local Grok pilot code and transcripts.

## Upgrading from 0.6.x

Ordinary direct and group message framing remains compatible. The beta's checks
covered sixteen bidirectional Python exchanges with 0.6.0 through 0.6.3; they do
not establish compatibility for every host or mixed-version governance setup.

- Strict receive-result consumers must allow the additional `charter_info` field.
- Recreate legacy unbound announcement channels with the new key-bound IDs.
- Active gateways own membership changes. Legacy or non-creator gateway
  invitations do not establish membership-governance authority; use a fresh,
  creator-invited gateway conversation where required.
- Create fresh requests and votes rather than replaying old signed actions.
  Previously provisioned credentials may require fresh provisioning.
- API responses are bounded, redirects cannot forward gateway credentials, and
  identity generation refuses to overwrite an existing identity.

See the beta's [compatibility table](v0.9.0-beta.1.md#compatibility-with-06x) for
details. A client package pin does not isolate a deployment from changes to shared
relay or gateway services.

## Charter and gateway boundaries

The charter protocol remains experimental and unwitnessed. Its proofs establish
an agent's complete history and latest recorded state within a signed registry
snapshot; applications choose their freshness policy and assess charter content.
The registry does not certify compliance with a charter.

Gateway operators remain trusted to enforce configured signature thresholds.
Credential replacement/revocation is not yet quorum-governed, and `did:web`
resolution requires an appropriate caller-controlled egress policy. See the
[audit report](../audits/2026-10-30-charter-release-audit.md) for remaining boundaries.
